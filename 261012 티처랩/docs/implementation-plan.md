# 학급 경영 앱 단계별 구현 및 자동 검수 계획

최신 변경(2026-10-14): [로그인·직접 적립 추가 계획](./login-and-self-praise.md)의 Step 2.6~2.7, 3.6~3.8과 Gate G02-07~08, G03-09~13을 포함한다. Phase 5·6은 현재 범위에서 제외하고 Phase 7은 Phase 4를 선행 단계로 삼는다. 아래 과거 Phase 5·6의 설명은 참고 이력이며 구현 대상이 아니다. 샘플 로직 검사 통과는 실제 앱 Phase 통과를 뜻하지 않는다.

버전 0.1 · 2026년 10월 12일 · 상태 계획 수립 완료, 구현 미시작

이 계획은 기능 구현과 검수를 하나의 작업 단위로 묶는다. 각 Phase는 여러 Step으로 진행하고, 마지막에 자동 검수 Gate를 실행한다. 필수 검수에 실패하면 원인을 수정하고 다시 검수하며, 통과한 뒤에만 다음 Phase로 넘어간다.

기준 문서: [PRD](../학급경영_칭찬관리_PRD.md), [도메인 정의](./domain-model.md), [폴더 구조](./folder-structure.md). 자동 검수 항목과 단계 의존성은 [검수 명세](./qa/phase-gates.json)에도 기록한다. 현재 작성한 것은 계획과 명세이며, 앱·실행 스크립트·제품 테스트는 아직 구현하거나 실행하지 않았다.

추가 반영: [학기별 칭찬판과 보상](./stamp-and-rewards.md)을 기준으로 개인 네 영역 각 30칸은 Phase 3, 모둠 두 영역 각 15칸과 학급온도계·20개 빈 보상란은 Phase 4에서 구현한다. 온도계를 P1에서 P0로 앞당긴다.

여기서 완료는 **정해진 환경에서 필수 동작·예외·권한·회귀 검증을 통과하고, 알려진 기능 오류가 남아 있지 않은 상태**다. 자동 검수만으로 모든 기기와 모든 실제 상황에서 결함이 없음을 보장할 수는 없으므로, 실제 수업 사용성 확인은 별도 출시 조건으로 관리한다.

## 2 모든 Phase에 적용할 완료 규칙

### 2.1 자동 검수 Gate

Phase 1에서 `verify:phase`와 `verify:release` 실행기를 만든다. 실행기 이름은 계약이며 현재 존재하는 명령이 아니다. 기술 스택을 정하면 정확한 실행 방법을 README에 기록한다.

각 Gate는 다음 순서로 실행한다.

1. 대상 Phase의 Step 구현과 필수 검수 ID가 모두 등록됐는지 확인한다.
2. 코드 구문·타입·정적 검사, 도메인 의존 경계, 배포용 빌드를 검증한다.
3. 해당 Phase의 업무 규칙 테스트를 실행한다.
4. 테스트 전용 실제 DB에서 저장·제약·트랜잭션·동시성 테스트를 실행한다.
5. 서버에 직접 요청해 인증·역할·학급·개인 데이터 접근을 검증한다.
6. 브라우저에서 교사·학생의 사용자 흐름과 실패 복구를 검증한다.
7. 앞서 완료한 Phase의 필수 회귀 항목을 재실행한다.
8. 실행 대상 소스와 환경, 검수 결과, 실패 자료를 보고서로 저장한다.

문서만 다루는 Phase 0에서는 규칙과 검수 명세의 정합성을 확인한다. 아직 없는 제품 기능 테스트를 통과했다고 기록하지 않는다. Phase 1에서는 실패 감지와 실행기 자체를 검증하고, 이후 Gate는 해당 시점에 구현한 제품 범위를 실제로 검증한다.

### 2.2 통과와 실패의 판정

- 필수 검수 전부 PASS, 미해결 기능 결함 0건, 현재 소스와 일치하는 검수 보고서가 있어야 Phase를 완료한다.
- 필수 테스트 누락, 테스트 0개 실행, skip, timeout, DB 미접속, 브라우저 미실행, 외부 인증 환경 부재는 성공이 아니다. 환경 문제는 BLOCKED로 기록한다.
- 실제 저장·권한 테스트를 mock 결과로 대체하지 않는다. 외부 서비스 모의 응답은 실패 주입용으로 사용할 수 있지만 실제 연결 검증과 구분한다.
- 테스트를 삭제하거나 기대값을 현재의 잘못된 동작에 맞춰 낮춰서 통과시키지 않는다. 정책 변경이 필요하면 결정 기록·요구사항·검수 조건을 함께 바꾼다.
- 실패 후 재시도에서 우연히 성공해도 원인을 확인하지 않은 불안정 테스트는 통과로 처리하지 않는다.
- 검수 이후 코드나 스키마가 바뀌면 이전 결과를 그대로 재사용하지 않는다. 변경 영향 범위를 재검증하고 해당 Phase Gate를 다시 실행한다.
- 코드 커버리지 숫자 하나로 완료를 판정하지 않는다. 업무 불변 조건, 접근 권한, 데이터 보존과 실패 복구를 실제로 검증한다.

### 2.3 자동 수정과 보고

구현 담당 에이전트가 실패 자료 확인 → 원인 수정 → 관련 테스트 실행 → Phase Gate 재실행을 수행한다. 통과하면 매 Step마다 승인을 요청하지 않고 계획된 다음 Phase로 진행한다. 사용자 입력·외부 권한·환경 변경이 꼭 필요한 경우에는 해결 가능한 부분을 먼저 처리하고 구체적인 차단 사유를 보고한다.

Phase 종료 보고에는 구현 결과, 검수 통과 수, 실패·미실행 수, 주요 증거 경로, 다음 단계를 적는다. 자동 검수 상태는 NOT_STARTED, IN_PROGRESS, FAILED, BLOCKED, PASSED로 관리하며 현재 모든 Phase는 NOT_STARTED다.

## 3 Phase 0 구현 기준과 실행 환경

**목표**: 구현 중 요구 해석이 흔들리지 않도록 동작 기준과 테스트 환경을 정한다.

**Steps**

1. **Step 0.1 요구 추적표 작성** — PRD F01~F08 및 정보 보호·운영 요구를 도메인, Phase, 검수 ID에 연결한다. P0와 P1을 구분한다.
2. **Step 0.2 제품 정책 기준 기록** — 공개 범위, 최근 수상 기준, 정정 시 기준일, 답글 확인 범위, 학년도 변경을 결정 기록으로 남긴다. 기존 제안은 작업 기본값으로 사용하고 사용자 확정과 구분한다.
3. **Step 0.3 기술과 실행 환경 선택** — 기존 설치 상태, 프레임워크·DB·인증·브라우저 테스트 수단을 확인하고 한 조합으로 고정한다. 선택 시 공식 문서로 현재 지원 상태를 확인한다. 개발·테스트·출시 환경을 분리한다.
4. **Step 0.4 검수 데이터 정의** — 교사 2명, 서로 다른 학급 2개, 각 학급의 학생·모둠·편지, 활성·전출 학생을 포함한 가상 데이터를 정의한다. 성능 검증용으로 한 학급 40명을 준비한다.
5. **Step 0.5 날짜와 경쟁 상황 정의** — 서울 자정, 주간 경계, 연말 ISO 주차, 14일 경계, 동일 요청 재시도, 게시와 취소 동시 실행의 기대값을 작성한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G00-01 | 요구 추적표 검사 | 모든 P0 요구에 담당 Phase와 필수 검수 ID가 있음 |
| G00-02 | 정책 충돌 검사 | 같은 정책의 상충 정의가 없고 미확정 사항에는 작업 기본값 또는 출시 차단 조건이 있음 |
| G00-03 | 실행 환경 사전 점검 | 선택한 런타임·테스트 DB·브라우저 실행 방법을 실제 확인하고 버전·접속 방법을 기록 |
| G00-04 | 검수 명세 검사 | ID 중복·없는 선행 단계·순환 의존이 없고 필요한 가상 데이터와 기대값이 정의됨 |

산출물: 요구 추적표, 기술 결정 기록, 제품 정책 기록, 실행 환경 기록. 실제 데이터 보관·배포 주체 등 출시 정책의 미확정은 Phase 8 출시 조건에 남긴다.

## 4 Phase 1 프로젝트와 자동 검수 기반

**목표**: 이후 모든 기능이 같은 방식으로 빌드되고 검증되도록 기반을 만든다.

**Steps**

1. **Step 1.1 앱 골격 생성** — 폴더 설계에 맞춰 진입점, UI, 계약, 서버 모듈과 bootstrap을 만든다. 최초 흐름에 필요한 폴더만 생성한다.
2. **Step 1.2 데이터 기반 구현** — DB 연결, 마이그레이션, 트랜잭션, 학급 단위 잠금, 주입 가능한 시계·ID 생성기를 준비한다.
3. **Step 1.3 실행 경계 구현** — 요청 형식 검사, 오류 응답, 서버 전용 코드 보호, 공통 변경 로그와 민감값 제거를 구현한다.
4. **Step 1.4 검수 실행기 구현** — 단위·실제 DB·권한·브라우저 테스트를 연결하고 phase-gates.json의 필수 ID를 실제 테스트 파일에 매핑한다. 없는 검수 ID는 실패 처리한다.
5. **Step 1.5 실패 자료 수집** — 보고서, 서버 로그, 브라우저 trace와 실패 화면을 보관한다. 사용 환경에 CI가 있으면 같은 실행기를 연결하고, 없으면 로컬 실행으로 검수한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G01-01 | 설치·정적 검사·빌드·기동 | 고정된 의존성으로 설치되고 배포용 빌드와 기본 화면 기동 성공 |
| G01-02 | 빈 DB 구성과 트랜잭션 | 마이그레이션 성공, 의도적 실패 시 부분 저장 없이 롤백 |
| G01-03 | 코드 경계 | client→server, domain→DB, 도메인 내부 우회 import를 검사기가 잡음 |
| G01-04 | 검수 실행기 실패 감지 | 의도적 실패·누락·skip·테스트 0개·DB 장애를 PASS로 보고하지 않음 |
| G01-05 | 브라우저 및 증거 생성 | 실제 브라우저 smoke 성공, 현재 소스 식별자와 검수 결과 보고서 생성 |

G01-04의 의도적 실패는 별도의 실행기 자기검증에서 기대되는 결과다. 실제 Phase 결과의 필수 제품 테스트를 실패시킨 채 통과하는 예외가 아니다.

## 5 Phase 2 인증과 학급 및 학생

**목표**: 자기 학급과 자기 정보에만 접근할 수 있는 운영 기반을 완성한다.

**Steps**

1. **Step 2.1 교사 인증 구현** — 로그인·로그아웃·세션 만료·재인증·계정 복구 경로를 연결한다.
2. **Step 2.2 학급과 명단 구현** — 학급 생성, 번호·이름 등록과 변경, 중복 번호 및 정원 검증을 구현한다. 학기별 기간·활성 상태를 정의하고 기간 중복을 막는다.
3. **Step 2.3 학생 접속 구현** — 개인 접속 수단 발급·재발급·폐기, PIN 보호, 실패 제한, 학생 로그인을 구현한다.
4. **Step 2.4 공용 기기 보호 구현** — 계정 전환 시 캐시와 입력 제거, 보호된 화면의 서버 권한 검사, 공개 모드 접속 범위와 교사 복귀 재인증을 만든다.
5. **Step 2.5 기본 수명주기 구현** — 학생 비활성화와 학급 보관 시 조회·기록·세션을 차단한다. 이후 모둠과 다른 도메인이 생기면 같은 흐름을 확장한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G02-01 | 로그인·만료·복구·재발급 | 유효한 접속만 성공, 이전 자격·만료 세션 거부, 복구 후 기존 접속 정책 적용 |
| G02-02 | 학급 격리와 권한 위조 | 다른 교사 학급·다른 학생·변조 역할 요청 모두 거부 |
| G02-03 | 명단 제약과 동시 등록 | 중복 번호·정원 초과 차단, 이름·번호 변경 후 ID 유지 |
| G02-04 | 전출·보관·계정 전환 | 기존 학생 세션도 접근 차단, 이전 사용자 데이터가 화면·응답·캐시에 남지 않음 |
| G02-05 | 입력과 세션 공격 경로 | 인증 시도 제한, 세션 고정·위조·선택한 인증 방식의 요청 위조 방어 동작 검증 |
| G02-06 | 교사·학생 브라우저 흐름 | 교사 학급 생성→학생 접속까지 실제 DB와 두 브라우저 문맥에서 성공 |

실제 계정 복구가 외부 제공자에 의존하면 제공자의 테스트 환경에서도 검증한다. 연결이 없으면 해당 항목은 BLOCKED이며 가짜 로그인으로 완료 처리하지 않는다.

## 6 Phase 3 칭찬 기록과 학생 확인

**목표**: 가장 중요한 일상 흐름을 끝까지 사용 가능하게 만든다.

**Steps**

1. **Step 3.1 칭찬 모델 구현** — 학생·학기·영역별 30칸 판, 행동 날짜, 기록 시각, 취소 이력, 중복 요청 처리, 집계 자료 버전을 저장한다. 판 잠금 아래 상한을 검증하고 학기 간 기록을 분리한다.
2. **Step 3.2 교사 입력 구현** — 학생 카드, 영역 선택, 한 번 눌러 기록하는 모드, 저장 중·성공·실패 표시를 만든다.
3. **Step 3.3 정정 구현** — 5초 실행 취소, 이후 사유 있는 취소, 과거 날짜 기록과 교사 이력을 구현한다.
4. **Step 3.4 학급 첫 화면과 학생 및 공개 조회 구현** — 학급 진입 시 우리 반 학급 규칙과 자주적인 어린이·긍정적인 어린이·적극적인 어린이·배려하는 어린이를 순서대로 표시하고 역할별 메뉴를 연결한다. 개인 칭찬판, 날짜별 도장, 본인 합계, 학급 공개용 DTO를 분리한다.
5. **Step 3.5 화면 갱신과 복구 구현** — 저장 후 학생 화면 반영, 재접속 시 새 조회, 응답 유실 재시도와 연결 실패 안내를 구현한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G03-01 | 날짜·영역·취소 | 미래 날짜 거부, 정상 기록·취소가 학생 조회와 집계에 일치 |
| G03-02 | 중복 요청과 응답 유실 | 같은 요청을 동시·반복 전송해도 한 건, 같은 키의 다른 내용은 충돌, 서로 다른 요청은 별도 건 |
| G03-03 | 저장 실패와 재시도 | DB 실패·네트워크 단절을 성공처럼 보이지 않으며 재시도 후 누락·중복 없음 |
| G03-04 | 공개 데이터 경계 | 취소 사유·교사 이력·타 학생 개인 합계가 공개 DTO에 포함되지 않음 |

자동화는 한 번의 입력으로 저장 요청이 일어나는지 확인한다. 사람의 실제 1초 조작 시간은 Phase 8 사용성 검증에서 따로 측정한다.

## 7 Phase 4 모둠칭찬과 학급온도계

**목표**: 학생의 자율 점검과 교사의 정정을 권한에 맞게 제공한다.

**Steps**

1. **Step 4.1 편성 모델 구현** — 모둠, 소속 기간, 모둠장 지정 이력과 현재 소속 유일성을 구현한다.
2. **Step 4.2 편성 UI 구현** — 교사가 학생을 배치·이동하고 모둠장을 지정할 수 있게 한다.
3. **Step 4.3 모둠칭찬과 일별 점검 구현** — 정리·다했어요 각각 학기당 15칸과 교사 지급·취소를 구현한다. 모둠장 일별 체크는 독립적으로 유지하고 날짜 변경 시 누적 도장을 초기화하지 않는다.
4. **Step 4.4 권한·동시성 구현** — 현재 모둠장의 오늘 수정, 교사의 과거 정정, version 충돌 안내를 구현한다.
5. **Step 4.5 전출 흐름 확장** — 학생 비활성화·모둠 소속 종료·모둠장 해제·접속 폐기를 같은 업무로 묶는다.
6. **Step 4.6 학급온도계 구현** — 교사 전체 칭찬당 +5도, 0~100도 상한, 취소와 주기 보관을 구현한다. 개인·모둠 칭찬과 자동 연동하지 않는다.
7. **Step 4.7 온도별 보상표 구현** — 5~100도의 20개 빈 입력란, 교사 편집·학생 조회, 새 주기 빈 보상표를 구현한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G04-01 | 소속과 모둠장 제약 | 동시 이동에도 현재 소속 최대 하나, 모둠당 현재 모둠장 최대 한 명 |
| G04-02 | 쓰기 권한 | 일반 학생·다른 모둠장·이전 모둠장 수정 거부, 현재 모둠장 오늘 수정 성공 |
| G04-03 | 날짜와 충돌 | 다음 날짜에 미완료로 시작, 반복 요청 중복 없음, 오래된 version의 덮어쓰기 거부 |
| G04-04 | 전출 원자성 | 중간 실패 주입 시 전체 롤백, 성공 시 소속·모둠장·접속 상태 모두 변경 |
| G04-05 | 브라우저 점검 흐름 | 두 항목 완료·교사 정정이 학생 및 공개 화면에 일치하며 개인 칭찬 수는 그대로 유지 |
| G04-06 | 모둠 15칸 상한 | 정리·다했어요 각각 15칸, 16번째·동시 초과 지급 거부, 취소·재지급·학기 분리, 학생 체크만으로 도장 생성 없음 |
| G04-07 | 학급온도계 | 0도 시작·20회로 100도, 21번째 거부, 95도 동시 증가·중복 요청·취소에서 범위와 5도 단위 유지, 학생 조절 차단 |
| G04-08 | 빈 보상표 | 5~100도 20개 초기 내용 모두 빈칸, 빈 내용으로도 온도 증가, 교사만 편집, 새 주기 보상표 빈칸·과거 보존 |

## 8 Phase 5 시상 추천과 게시

**목표**: 추천 결과를 설명하고 교사의 승인과 정정을 안전하게 반영한다.

**Steps**

1. **Step 5.1 추천 엔진 구현** — 점수 집계, 최근 14일 후순위, 동점 순서, 고정 시드, 영역 순환, 1인 1상 규칙을 순수 함수로 구현한다.
2. **Step 5.2 회차와 버전 구현** — 주간 회차, 입력 스냅샷, 자료 버전, 검토 상태, 게시 버전과 철회를 저장한다.
3. **Step 5.3 교사 검토 UI 구현** — 기간·추천 이유·후보 부족·최근 수상 여부를 표시하고 사유 있는 교체와 게시 미리보기를 제공한다.
4. **Step 5.4 게시 일관성 구현** — 학급 잠금 아래 자료 버전을 재확인하고 게시한다. 칭찬 변경·전출·다른 수상 변경과 경합해도 오래된 초안을 게시하지 못하게 한다.
5. **Step 5.5 공개와 정정 구현** — 학생 칭찬 소식에 게시 버전만 표시하고 정정 초안 작성 중 기존 공개 결과를 유지한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G05-01 | 추천 정답 사례 | 비수상자 우선·최근 수상자만 있음·0점·후보 부족·동점·여러 영역 고득점 사례 모두 기대 결과와 일치 |
| G05-02 | 불변 조건 | 다양한 고정 시드 입력에서 한 회차 학생 중복 없음, 부문 최대 한 명, 무단 후보 추가 없음, 동일 입력의 결과 재현 |

| G05-04 | 동시 게시·정정 | 게시와 칭찬 취소·전출의 실행 순서를 제어한 테스트에서 오래된 초안 게시 및 부분 게시 없음 |
| G05-05 | 버전·철회·중복 요청 | 정정 전 기존 결과 유지, 게시 요청 중복 공지 없음, 철회 회차 제외, 정정이 수상 횟수를 늘리지 않음 |
| G05-06 | 공개 권한과 브라우저 흐름 | 후보·근거는 교사만 조회, 검토→게시 이후에만 학생에게 확정 결과 노출 |

동시성 검증은 실제 DB와 동기화 지점을 사용한다. 임의의 지연 시간을 넣어 우연히 문제가 안 생긴 결과를 증거로 사용하지 않는다.

## 9 Phase 6 비밀편지와 지도 노트

**목표**: 공개 기능과 분리된 학생·교사 소통을 완성한다.

**Steps**

1. **Step 6.1 편지 데이터 구현** — 대화·불변 메시지·추가 글·교사 전용 노트를 분리하고 글자 수를 검증한다.
2. **Step 6.2 학생 작성 구현** — 제출·추가 글·상태 조회·답글 확인과 작성 중 이탈 안내를 제공한다.
3. **Step 6.3 교사 응답 구현** — 재인증, 명시적 읽음 표시, 답글, 노트 작성·수정을 제공한다.
4. **Step 6.4 공개 차단 구현** — 응답 DTO, 캐시, 서버 렌더링 데이터, 알림·실시간 채널·로그를 검사해 민감 정보 경계를 적용한다.
5. **Step 6.5 공용 기기 검증** — 비활동 잠금, 로그아웃·계정 전환·공개 모드·뒤로 가기·다중 탭에서 재조회 권한을 검증한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G06-01 | 소유자·학급·재인증 | 학생 본인과 재인증된 담당 교사만 열람, 모둠장·타 교사·타 학생·만료 재인증 모두 거부 |
| G06-02 | 메시지 상태 | 조회만으로 읽음 변경 없음, 답글 시점 이후 새 글은 미확인, 제출 원문 변경 불가 |
| G06-03 | 노트와 공개 경계 | 학생 응답·공개 화면·알림·로그·브라우저 저장소에 노트나 편지 테스트 식별 문구가 노출되지 않음 |
| G06-04 | 공용 기기·다중 탭 | 로그아웃·전출·공개 전환 이후 민감 내용 재조회와 캐시 복원이 차단됨 |
| G06-05 | 입력과 저장 실패 | 1~2,000자 조건·스크립트 입력 안전 표시·실패 안내·중복 제출 방지 동작 |
| G06-06 | 비공개 전체 흐름 | 학생 제출→교사 확인·답글→해당 학생 확인 성공, 다른 학생에게 변화 노출 없음 |

민감 노출 검사에는 실제 상담 내용 대신 고유한 가상 식별 문자열을 사용한다. 테스트 결과와 trace에도 실제 학생 데이터는 사용하지 않는다.

## 10 Phase 7 운영 수명주기와 통합

**목표**: 정상 수업뿐 아니라 전출·학년 종료·장애·데이터 관리까지 운영 가능하게 한다.

**Steps**

1. **Step 7.1 화면 통합** — 학급 규칙 첫 화면, 교사 홈, 학생 홈, 교실 공개 화면의 실제 조회를 연결한다. 빈 상태·실패·로딩·권한 만료 안내를 통일한다.
2. **Step 7.2 수명주기 완성** — 전출과 보관의 효과를 칭찬·모둠·시상·편지 전체에 적용하고 다음 학년도에는 새 명단을 만든다.
3. **Step 7.3 내보내기 구현** — 공개 칭찬 자료와 민감 기록을 분리하고 담당 교사만 선택한 범위를 내려받게 한다. 파일 접근과 만료를 검증한다.
4. **Step 7.4 삭제와 복구 구현** — 일반 취소·보관·영구 삭제를 구분하고 작업 재시도, 파생 데이터·임시 파일·outbox 처리, 백업 만료 및 복원 후 재삭제 절차를 구현한다.
5. **Step 7.5 전달 실패 복구** — outbox 중복 처리 방지, 재시도, 실시간 재접속, 실패 계측을 연결한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G07-01 | 전체 수명주기 | 전출·보관 후 모든 해당 API와 실시간 구독에 일관된 권한 반영, 새 학년에 기존 기록 자동 이월 없음 |
| G07-02 | 내보내기 범위 | 해당 교사·선택 학급·선택 데이터만 포함, 민감 내용 기본 혼합 없음, 만료 파일 접근 거부 |
| G07-03 | 삭제·재시도 | 가상 학급의 삭제가 정해진 범위에 적용되고 중간 실패 재시도에도 누락·타 학급 영향 없음 |
| G07-04 | 백업 복원 훈련 | 테스트 백업 복원 후 삭제 이력 재적용, 복원 전후 기대 레코드·삭제 상태 일치 |
| G07-05 | 전달과 재접속 | 같은 이벤트 재전달에도 부작용 중복 없음, 연결 복구 후 서버 상태와 화면 일치 |
| G07-06 | 통합 브라우저 흐름 | 교사·학생·공개 화면 전체에서 주요 이동과 오류 복구가 가능하며 민감 데이터 경계 유지 |

실제 보관 기간을 임의로 법정 기준처럼 정하지 않는다. 테스트에서는 가상 정책과 주입한 시계로 삭제·백업 만료 메커니즘을 검증하고, 실제 운영 정책의 확정 여부는 Phase 8에서 별도로 확인한다.

## 11 Phase 8 P0 출시 후보 검수

**목표**: 개발 중 개별 검증을 실제 출시 후보 환경에서 다시 확인한다.

**Steps**

1. **Step 8.1 깨끗한 환경 검증** — 고정된 소스로 재설치·빌드·마이그레이션하고 실제 운영과 같은 방식으로 서버를 기동한다. 개발 전용 인증 우회가 없는지 확인한다.
2. **Step 8.2 전체 회귀 검증** — Phase 1~7의 필수 항목과 P0 요구 추적표를 전부 대조한다. 테스트·실제 API·브라우저 흐름을 함께 실행한다.
3. **Step 8.3 성능 검증** — 교사 1명과 학생 40명의 세션을 유지하며 칭찬 저장·반영, 시상, 편지 조회의 응답을 측정한다.
4. **Step 8.4 화면·접근성 검증** — 휴대전화·태블릿·PC 화면 크기, 키보드 입력, 포커스 이동, 오류 안내를 자동 검사하고 실패 화면 및 대표 화면을 직접 점검한다.
5. **Step 8.5 배포·복구 준비** — 설정 검증, 상태 확인, 백업 복구, 이전 앱 버전 복귀 및 스키마 호환성 절차를 검증하고 실행 안내서를 만든다.
6. **Step 8.6 실제 운영 준비 확인** — 대상 기기, 계정·배포 환경, 학생 데이터 운영 정책을 확인한다. 교사의 1초 입력·3분 시상 준비와 교육적 사용성을 파일럿에서 확인할 계획 및 결과를 별도로 기록한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G08-01 | 깨끗한 설치와 이전 버전 갱신 | 신규 DB 설치와 직전 스키마에서의 갱신 성공, 기존 가상 기록 보존 |
| G08-02 | 전체 필수 회귀 | P0 필수 ID 전부 실행·통과, skip·미실행·미해결 기능 결함 0건 |
| G08-03 | 부하와 반영 시간 | 정의한 시험 환경에서 칭찬 저장 p95 ≤2초, 저장 후 학생 반영 p95 ≤3초, 누락·중복·예상 밖 서버 오류 0건 |
| G08-04 | 지원 화면과 접근성 | 지원 브라우저·뷰포트의 핵심 흐름 통과, 가로 넘침·조작 불가·자동 검사상 중대 접근성 오류 없음 |
| G08-05 | 출시 설정과 복구 | 인증 우회·샘플 비밀값 없음, 배포 기동·상태 확인·호환 버전 복귀·DB 복구 절차 검증 |
| G08-06 | 증거와 요구 추적 | 현재 소스 기준 보고서와 모든 P0 검수 매핑 존재, 불안정 실패·누락 증거 없음 |

**성능 시험 제안 조건**: 워밍업 1분 뒤 10분 측정, 학급당 교사 1명·학생 40명 연결, 교사 칭찬 입력 초당 1건과 학생 조회·실시간 구독을 함께 수행한다. 최소 600건의 칭찬 저장 표본과 해당 전달 표본을 수집한다. 서버 사양, DB, 브라우저, 네트워크 지연, 표본 수를 보고서에 적는다. 환경이 달라지면 조건을 명시하고 재측정한다. 이 시험은 학교 전체 동시 접속 성능을 주장하는 근거가 아니다.

**출시 조건을 별도로 관리**: 자동 Gate PASS는 기술적 출시 후보 상태다. 실제 기기 사용성·교육적 적합성, 필요한 운영 정책·계정·배포 환경이 미확인이라면 출시 준비 완료로 보고하지 않는다. 사람의 조작 시간과 수업 만족도를 자동 테스트 통과로 대체하지 않는다. 자동 검수 보고서와 운영 확인 기록이 모두 충족될 때 P0 출시 준비 완료로 표시한다.

## 12 Phase 9 P1 수업 도구 확장

**목표**: P0가 안정된 뒤 발표 뽑기를 추가한다. 학급온도계는 Phase 4에서 이미 구현하고 검수한다.

**Steps**

1. **Step 9.1 발표 추첨 구현** — 수업 세션, 활성 참여 대상, N명 중복 없는 추첨, 이미 뽑힌 학생 제외와 초기화를 만든다.
2. **Step 9.2 칭찬 연결** — 추첨 결과의 명시적 버튼으로만 기존 칭찬 API를 호출하고 학생 자격을 다시 확인한다.
3. **Step 9.3 추첨 세션 이력 구현** — 수업별 대상·결과·이미 뽑힌 학생 제외와 새 수업 초기화를 검증한다.
4. **Step 9.4 화면 연결** — 학생·교실 공개 화면에 허용된 추첨 결과를 연결한다. 애니메이션 생략을 제공한다.
5. **Step 9.5 전체 회귀 및 출시 후보 재검수** — P1 전용 테스트와 P0 검수, 성능·권한 검증을 최종 확장 소스에서 다시 실행한다.

**자동 검수와 성공 조건**

| 검수 ID | 검증 | 통과 조건 |
| --- | --- | --- |
| G09-01 | 추첨 규칙 | 후보 0명·N 초과 거부, 비활성 학생 제외, 같은 회차 중복 없음, 제외·초기화 규칙 정확 |
| G09-02 | 수동 칭찬 연결 | 추첨만으로 도장 생성 없음, 버튼 실행 후 정상 생성, 중복 요청에도 한 건 |
| G09-03 | 추첨 세션 이력 | 같은 수업 제외 규칙 정확, 새 수업 대상 초기화, 과거 추첨 이력 유지 |
| G09-04 | 공개·권한·브라우저 | 학생 임의 추첨 거부, 교사 추첨·공개 반영·애니메이션 생략 동작 |
| G09-05 | 확장 후 회귀 | P0 필수 검수와 G08-01~06을 확장 소스에서 재실행해 모두 통과 |

추첨 검증은 난수 의존 테스트의 불안정성을 피하기 위해 고정 난수 입력과 알고리즘의 선택 범위를 검증한다. 작은 표본의 우연한 빈도 차이만으로 공정성 성공·실패를 단정하지 않는다.

## 13 검수 실행 명세와 증거

### 13.1 자동 실행기의 계약

다음 호출 형식은 Phase 1에서 구현할 계약의 예시다. 사용할 패키지 관리자는 Phase 0에서 결정한다.

```text
verify:phase --phase 3
verify:phase --phase 5 --include-prerequisites
verify:release --scope p0
verify:release --scope p0+p1
```

기본 Phase 검수에도 완료된 선행 단계의 필수 회귀를 포함한다. `--include-prerequisites`는 그 동작을 명시하는 옵션이다. 원인 분석 중에는 특정 테스트만 실행할 수 있지만 그 결과를 Phase 전체 통과로 표시하지 않는다. 최종 `verify:release`는 전체 필수 검수를 포함한다.

`phase-gates.json`은 검수 ID·설명·의존성을 가진 계획 명세다. 이 파일의 존재 자체는 테스트 통과 증거가 아니다. Phase 1에서 각 ID에 실제 실행 대상과 필수 하위 사례를 연결한 매핑을 추가한다. 하나의 ID가 여러 테스트를 포함하면 필수 하위 사례 모두 실행됐는지 검사한다.

### 13.2 보고서 구조

```text
docs/qa/
├─ phase-gates.json                     # 현재 작성된 계획 명세
├─ requirement-matrix.md                # Phase 0에서 작성
└─ release-readiness.md                 # 운영·사용성 확인 기록

artifacts/qa/<source-id>/<run-id>/        # Phase 1 이후 실행 시 생성
├─ summary.json                         # 상태, 환경, 실행 ID, 실행 수, 소스 지문
├─ results.xml                          # 테스트별 결과
├─ failures/                            # 실패 trace·화면·정제된 로그
├─ performance.json                     # 표본과 p95 등 측정 결과
└─ phase-report.md                      # 구현 결과와 실패 원인·조치
```

source-id는 커밋뿐 아니라 미커밋 변경·스키마·잠금 파일·검수 설정을 포함한 지문으로 만든다. 보고서 생성에 따른 파일 변경은 지문 계산에서 제외한다. 검수 도중 소스가 바뀌면 해당 실행은 오래된 결과로 표시한다. 가상 데이터만 사용하고 결과물에도 인증 비밀값을 남기지 않는다.

### 13.3 실패 처리 순서

1. **재현** — 실패한 검수 ID, 요청, 가상 데이터와 소스 버전을 고정한다.
2. **분류** — 업무 규칙, 권한, 저장·동시성, 화면, 환경, 불안정 테스트 중 원인을 구분한다.
3. **수정** — 문제를 소유한 도메인 또는 기반 계층에서 고친다.
4. **확인** — 해당 사례를 먼저 재실행하고 통과하면 Phase Gate를 실행한다.
5. **보고** — 원인과 수정, 마지막 검수 결과를 남긴다. 원인 미확인 실패가 남으면 다음 Phase로 넘어가지 않는다.

## 14 구현 착수 시 실행 순서

처음에는 Phase 0의 기준을 기록하고 Phase 1의 자동 검수 기반을 만든다. 이후 Phase 2~7을 순서대로 구현하고, 각 종료 Gate를 직접 실행해 통과 결과를 남긴다. Phase 8에서 P0 출시 후보를 검수한다. P1은 별도 Phase 9로 진행하며 추가 후에도 P0 전체 검수 기준을 유지한다.

계획 수립 시점에 제품 코드를 작성하거나 테스트 성공을 가정하지 않는다. 구현을 진행할 때 이 문서를 작업 순서와 완료 판정의 기준으로 사용한다.
